# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Aetheria is a playable Tower Defense MVP: Vite + React + TypeScript, battle board on a plain `<canvas>`. No game engine. `README.md` covers gameplay and the extend-by-data checklist; this file covers internal wiring.

## Commands & environment

Scripts in `package.json`: `dev`, `build`, `typecheck`, `lint`. **No test framework** — don't reference `npm test`. Verify with `npm run typecheck` plus exercising the app in the browser preview. Environment is **Windows / PowerShell**; Vite dev server on port 5173 (auto-bumps if taken).

**Update the patch notes on every GitHub push.** Whenever you push (or the user asks you to push) to GitHub, first prepend a new entry to the `PATCH_NOTES` array in `src/ui/components/PatchNotes.tsx` (newest first) summarizing the user-facing changes in that push, dont miss a thing. This changelog is shown in-game via the 📝 Patch Notes button next to the ⚙️ Settings icon in the `TopBar`. Do this as part of the push, not as a separate step to be reminded about.

**Don't block on browser screenshots.** The Browser pane is often not displayed, so `computer` screenshots time out — that's expected, not a failure to chase. A clean `npm run typecheck` plus a `read_console_messages`/`preview_logs` error check is sufficient. To drive the app headlessly, `import('/src/...')` modules in the page and construct a `GameEngine` (private methods callable via `engine['name']`), or seed `localStorage['aetheria-td:state']` and reload.

## Art & music direction

**All art and music direction lives in [`ART_DIRECTION.md`](ART_DIRECTION.md)** — the visual vision, canvas + UI palettes, typography and icon rules, figure/sprite conventions (anatomy parts, the three enemy views, `footLiftFor`, the figure compositor and its cache rules), board lighting/mood/VFX/props, sound effects and background music (direction, current tracks, instrument palette, how to add a chapter theme). Read it before any sprite, prop, VFX, UI-styling, SFX or music work, and keep it updated when the look or sound changes. When Generating sprites dont show me the end result.

## Architecture

Strict one-directional layering — `ui → application → domain`, with `engine` a self-contained sibling. Inner layers never import outer ones. See `README.md` for the file tree. Load-bearing boundaries:

**`domain/` is pure data + rules.** Catalogs (`units`, `enemies`, `levels`, `rarity`) are plain objects; adding content is a data edit, never an `engine`/`ui` code change. **Single source of truth is the rule that keeps displays from drifting**: when a number appears on more than one surface, route it through one shared helper rather than recomputing inline. `masteryStats(unit, tier, purchased)` (mastery-adjusted damage/attack-speed/range) feeds the engine's `towerStats`, stat panels, `masteryUpgradeDeltas` ("+N DMG" labels), and the placement-range preview; yields go through `masteryHarvest`, crit through `critChanceFor`/`critMultiplierFor`, in-stage upgrade prices through `masteryUpgradeCost`. Attack speed displays via `formatAttackSpeed` (fractional from mastery multipliers).

**Levels are multi-lane.** A `LevelDef` holds `lanes: LaneDef[]`, each with its own `pathTurns` **and** `waves`. `domain/levels.ts` authoring accepts single-lane shorthand (`path`+`waves`) or explicit `lanes`; `buildLevels`/`specLanes` normalize both. Lanes may run separately or **converge** (share a tail of turn cells → enemies merge, shared exit dedupes to one castle). The engine precomputes per-lane geometry (`GameEngine.lanes`); each `Enemy` has a `laneIndex`; wave `i` spawns every lane's `waves[i]` in parallel; `totalWaves` = longest lane. **Victory requires clearing the final wave across all lanes** — killing the boss doesn't end the stage.

**Wave authoring & set-piece lanes.** A `WaveDef` is groups of `{ enemyId, count, spacing?, delay? }`: `spacing` (default `DEFAULT_SPACING`) is the gap between spawns *within* a group; `delay` offsets a group from the **previous group's start** (groups overlap unless delayed past it) — see `buildSpawnQueue`. A lane may set `revealAtWave: N` to stay hidden (undrawn, non-blocking, non-spawning) until wave N begins, then its path *rolls out* (`LANE_REVEAL_TIME`, drawn as a partial polyline via `laneRevealFraction`) and its cells start blocking building. A boss spawning on such a lane gets a throne-**rise**: `Enemy.rise` (1→0 over `RISE_TIME`) freezes it in place and untargetable while the renderer lifts it `RISE_LIFT`px and blends its sprite seated→walking (the Throne Room king). Targeting `first`/`last` compare `remainingToExit` (cross-lane distance to base), not per-lane progress. Bosses live in `domain/enemies.ts` `BOSS_META` (one per level, id `boss<levelId>`); stats come from an escalating curve, but any `BossMeta` field (`health`/`speed`/`reward`/`damageToBase`/`radius`) overrides its default. Don't add units to stages on your own, unless asked.

**The engine is framework-agnostic and headless.** `new GameEngine(level, startingGold, masteryUpgrades?, rng?)` — injectable `rng` (default `Math.random`) makes crit deterministic. It exposes mutable public fields (`currency`, `enemies`, `towers`, `masteryEarned`, …) and intent methods (`placeUnit`, `upgradeTower`, `startWave`, `deployStats`), and imports no React. `renderer.ts` only *reads* an engine snapshot — no rules. **Damage is mixed-timing**: melee (Swordsman) and line-AoE (Spearman) apply instantly; arrows/bolts (Archer, Crossbow, Wizard gust) are homing `Projectile`s carrying pre-rolled damage applied *on impact*, dropping harmlessly if the target dies first. All damage funnels through `damageEnemy(enemy, amount, source?)` — the choke point for kill credit and engine-only on-hit effects (e.g. Gale Force knockback). `Shot`/`Burst`/`FloatingText`/`Puff` are cosmetic and self-decay.

**`GameScreen.tsx` is the only bridge between React and the engine.** It builds one `GameEngine` per level mount, drives it from a `requestAnimationFrame` loop, and copies engine fields into a React `Hud` snapshot each frame. Selection/hover live in refs so the loop reads fresh values without re-subscribing. Rewards bank **exactly once** at battle end via a `settledRef` guard — mastery EXP win *or* lose, gems only on first clear. Fast-forward sub-steps `engine.update(dt)` N times per frame (never one oversized `dt`) to keep motion/range fidelity.

**Procedural sprites cross the engine↔UI boundary.** `engine/sprites.ts` draws each champion silhouette, dispatched by `drawUnitSprite(shape, …)` and gated by `hasSprite(shape)`. `renderer.ts` paints board tokens with it; `ui/components/UnitSprite.tsx` calls the *same* functions for cards/menus, falling back to emoji for shapes without a sprite. To add one: write a `drawX`, extend `hasSprite` + `drawUnitSprite` — it appears on the board and every card at once. Enemies have a parallel `drawEnemySprite(id, color, view, faceLeft, dist, sit?)`/`hasEnemySprite(id)`; ids without a sprite fall back to the disc+emoji token in `drawEnemies`. Sprite authoring rules (complete `back` views, `footLiftFor` for oversized foes) are in `ART_DIRECTION.md`.

**Every figure goes through the figure compositor (`engine/figure.ts`).** Sprite functions draw flat fills; `paintFigure(ctx, draw, style, cacheKey?)` shades, rim-lights, outlines and composites them once, caching by `cacheKey` (LRU). Menus use the same pass via `ui/portrait.ts`. Bodies are built from `engine/anatomy.ts` parts. Shading, cache and anatomy conventions are in `ART_DIRECTION.md`.

**Board frame pipeline (`renderer.ts` `drawBoard`).** Per-engine state (baked terrain, `Lighting`, `Vfx`, prop lights) lives in a `WeakMap` keyed by the engine. Passes: baked ground (`terrain.ts`: seeded floor material per `BoardTheme.floor` + path material per `BoardTheme.pathKind`, re-baked only when the set of fully revealed lanes changes; a lane mid-reveal is stroked live) → depth-sorted world (props by `PROP_META.base`, champions, foes, corpses; tall `occludes` props fade to 50% when a figure stands behind) → normal-blend VFX → lighting (`lighting.ts`: half-res ambient darkness with lights punched out, additive glow, sun wash, soft-light grade) → glow pass (attacks, projectiles, additive VFX — never darkened) → vignette → unlit overlays (health bars, AoE guides, floaters, boss bars). Stage mood (darkness, light family, weather, grade, vignette, sun) is data in `domain/atmosphere.ts`, keyed by level id with per-section defaults. **The engine emits cosmetic `fx` events** (`hit`/`kill`/`blast`/`cast`/`dodge`/`breach`/`deploy`/`bossSpawn`, the visual twin of `sfx`, capped at 400); `drawBoard` drains them into `Vfx`, which owns particles (pooled, 900 cap), rings, flashes, slash crescents, light pulses, exposure lifts, hit recoil, corpses and screen shake (off under `prefers-reduced-motion`). Never read `fx` back in rules. Shared colours/easing/seeded RNG live in `engine/palette.ts` — pull ink, light families and materials from there rather than new hexes.

**Board dressing is cosmetic, but blocks placement.** Types in `domain/decor.ts`, drawing in `engine/props.ts`. A `BoardTheme` (checker colours = floor material tones, optional path stroke layers, `floor`/`pathKind` materials) and `DecorProp[]` come from level data `LevelDef.theme`/`.decor` (the castle stages ship both); a stage lacking `decor` data falls through to `drawLegacyDecor(levelId)`. Props render through the shared `drawProp` dispatch (same as the Level Designer palette/preview; re-exported from `renderer.ts`). Each kind has a `PROP_ART` entry (`origin` offset to its footprint centroid, `shadow`, cached `body` through the compositor with a quiet ink, animated `live` overlay for flames/water) and a `PROP_META` entry (draw `layer` ground/standing/overhead, `bounds`, `base` depth line, `occludes`, `lights`, `flames`, `chimneys`) — **when you redraw a prop, update its `bounds` too** (they size the compositor box and the occlusion test). Each also has a `PROP_FOOTPRINTS` cell footprint (multi-cell props anchor top-left). **`canPlaceAt` forbids building on path cells *and* decor cells** — `GameEngine.decorCells` comes from `decorCellKeys(level.decor)`, or the `CASTLE_DECOR_CELLS` mirror table for decor-less stages (keep it in sync with `drawLegacyDecor`). Theme/decor/atmosphere/boss are keyed by level **id**, so reordering a stage moves its room content, legacy decor case, `CASTLE_DECOR_CELLS` entry, `atmosphere` mood and `BOSS_META` entry together.

**UI art language.** Fonts, CSS tokens (top of `ui/styles.css`), the inline-SVG `Icon` set (no emoji in UI chrome), the menu backdrop (the blurred `DeskBackdrop`) and the summon ceremony are described in `ART_DIRECTION.md`.

**Modals must `createPortal(…, document.body)`.** Each `.screen` (a fade-in transform) establishes a containing block that would clip a `position: fixed` overlay. `Settings`, `ChampionDetail`, `MasteryTree`, `LevelDesigner` portal out; `.modal-backdrop` is a scrollable top-aligned flex container. Direct children of `.app` are lifted over the `Backdrop` by a zero-specificity `.app > :where(:not(.backdrop))` rule — keep it `:where()`, or it overrides the fixed TopBar corner and the fixed journal overlay (`.intro-root`), which then renders below the page. Sheets opened from inside the journal (`ChampionDetail`, `MasteryTree`) are lifted over `.intro-root` by `body:has(.intro-root) > .modal-backdrop`. (The Level Designer, in Settings → Developer, previews the design through the real `drawBoard` on a throwaway `GameEngine` (level id -1, so no id-keyed theme/legacy decor applies). It can start from any existing stage (first lane only), edits the path, props, floor/path materials and colours, previews any stage or chapter mood via the optional `LevelDef.atmosphere` override, and exports a `path:`/`theme:`/`decor:` snippet to paste into a `LevelSpec`. Moods themselves aren't exported; they stay keyed by id in `domain/atmosphere.ts`.)

**State + persistence go through the store.** `application/store.tsx` holds the single `GameState`, mirrors it in `stateRef`, and `commit()` persists every change through `infrastructure/storage.ts` (the sole `localStorage` point, namespaced `aetheria-td:`). UI reads state and calls actions via `useGame()`; it never touches storage or mutates state. Transitions in `gameState.ts` are pure. **Persistence is versioned**: bump `CURRENT_VERSION` and add a normalize line in `loadState` (e.g. `migrated.x = { ...(raw.x ?? {}) }`) whenever you add a `GameState` field.

**Teams gate deployment.** `GameState.team` is the ≤`MAX_TEAM_SIZE` (6) champions deployable in a stage; the in-stage deploy list reads `team`, not `ownedUnits`. Some mastery effects are *passive team bonuses* (e.g. Fresh Food starting gold via `masteryStartingGoldBonus`) applied from the roster without deploying.

**First-launch player intro & the custom avatar.** When there is no saved `GameState.player`, `App.tsx` renders `ui/components/PlayerIntro.tsx` in place of the normal shell — a journal cinematic + character-creation "Identification Page" where the player builds a portrait (`PlayerSpriteCreator`) and signs a name. `GameState.player` (a `PlayerProfile` = `{ name, sprite }`, `null` until finished) **is** the "intro completed" flag; `hasCompletedIntro(state)` gates it, so an existing (pre-`player`) save runs the intro once *without touching its progression*. The profile is committed **only at the very end** of the sequence (`onComplete` → `setPlayerProfile`); committing sooner would flip the gate and unmount the component mid-animation, so quitting halfway just replays the intro. The avatar is a **composed** sprite — unlike the monolithic champion `drawX` functions, `drawPlayerSprite(ctx, cfg, faceLeft)` in `engine/sprites.ts` assembles interchangeable parts from a `PlayerSpriteConfig` (`domain/playerSprite.ts`: build/skin/eyeColor/marking/hair/hairColor/facialHair/outfit/outfitColor/accentColor/headwear/headwearColor/cloak/cloakColor) yet obeys the same drawing conventions so it stands beside the champions. **Adding a part option** is a catalog entry in `playerSprite.ts` plus a branch in the matching `drawPlayer*` helper; a new *field* also needs its `SPRITE_CATEGORIES` row (with its creator tab `group` and tile `focus`), a default, a `randomPlayerSprite` line and a `normalizePlayerSprite` line (that line is the save migration). The creator (`PlayerSpriteCreator`) renders every option as a thumbnail tile through `PlayerSprite` (`framing` `full`/`snug`/`bust`, optional `weapon`). Journal ornaments (flourish, compass rose, page corners, wax seal, cover corners) are inline SVG in `ui/components/JournalArt.tsx`. **The journal is also the hub for champions and the bestiary** (there are no separate Champions/Bestiary screens). In review mode, three bookmarks (`JournalSection`: `profile` | `champions` | `bestiary`) switch between the adventurer's own pages, `JournalChampions` (team slots plus the roster, with `ChampionDetail`/`MasteryTree` opened from it) and `JournalBestiary`. `App` holds the open section in `journal` state; the home desk's journal opens it on `profile` and the campaign's Edit team on `champions`. The TopBar is not a bar: just gems, patch notes and settings floating in the top-right corner (`.screen` top padding clears them), with no navigation: the home desk's objects lead to each screen, and each of those screens has its own back button. The battle-profile numbers on both the journal plate and `ChampionDetail` come from `championStatTiles` in `ui/championStats.ts`. Persist the reconstructable config, never a rendered image; other systems redraw it via `ui/components/PlayerSprite.tsx` (`<PlayerSprite config={state.player.sprite} />`). `normalizePlayerSprite` repairs stored configs (colour fields accept any custom hex; unknown/removed part ids fall back to defaults), so it doubles as the migration when the catalog changes — `loadState` runs it via `normalizePlayerProfile` and a `null`/invalid result re-triggers the intro. Sound effects (`ui/introAudio.ts` and friends, all synthesized) and background music (`ui/music.ts`; `App` picks the track, `GameScreen` sets its intensity) are covered in `ART_DIRECTION.md`.

## Two distinct upgrade systems — do not conflate

- **In-stage upgrades** (`UnitDef.upgrades`): bought with **gold**, live on the deployed `Tower`, **reset every stage**. Sequential tiers; combat reads the tower's `effectiveStats`/`effectiveGenerate` fields.
- **Mastery skill tree** (`MASTERY_TREES` in `domain/mastery.ts`): bought with **permanent EXP**, stored per-champion in `GameState.masteryUpgrades`, applied **every** stage. Nodes are pure data with typed effect fields (`damageMult`, `rangeMult`, `critChanceBonus`, `generateMult`, `startingGoldBonus`, `throwEvery`, `adjacentDamageMult`, `rangeAuraMult`, `preloadShots`, `knockback`, `upgradeDiscount`…). `requires` makes a **sequential** tree, omitting it makes **parallel** nodes; `major: true` is a cosmetic gold outline; `exclusiveGroup` makes several learned nodes mutually exclusive (only one active). EXP comes from kills (`expForKill`; brutes/bosses worth more) and Farmer gold (`GOLD_PER_EXP`), banked once per stage via `awardMastery`.

**Purchased vs. active vs. effective** — three resolutions in `gameState.ts`, don't confuse them: `masteryUpgradesFor` (everything learned; MasteryTree "learned" markers), `activeMasteryUpgradesFor` (learned minus non-selected exclusive members; the tree's active markers), and `effectiveMasteryUpgradesFor` (active, or `[]` when the champion's `masteryDisabled` switch is on). Every **effect** surface reads the effective list — the engine and passive bonuses via `resolvedMasteryUpgrades(state)`, the in-stage panel/stat sheet/card yields directly.

**Adding a mastery effect:** add an optional `MasteryUpgradeDef` field, aggregate it in a `mastery*` helper, and consume that helper everywhere the stat is used (engine + every display) — the single-source rule keeps menus, the in-stage panel, and the simulation in agreement. Most effects fold into `masteryStats` at deploy. Some are **dynamic**, living only in the engine because they depend on live board state: board-position auras (`adjacentDamageMult` Better Morale, `rangeAuraMult` Guiding Gale) recomputed in `recomputeAdjacency` on every place/sell/upgrade, `preloadShots` (Quick Loader) per-frame firing state, and `knockback` (Gale Force) applied in `damageEnemy` with a per-enemy cooldown — surfaced through mutable `Tower`/`Enemy` fields the renderer reads.

## Hero activated abilities & mana

**Heroes (the three `rarity: 'hero'` player champions) have activated abilities + a mana pool — a third system, distinct from the two above.** An ability is data (`AbilityDef` on a tier-3 `UpgradeDef.ability`; no stat deltas that tier): `effectiveAbility(unit, tier)` resolves it, `applyTierStats` grants it to the `Tower` once (so a hero auto-levelling in gains it mid-stage). The player fires it from an icon in the in-stage panel (`AbilityButton` in `GameScreen`, driven by an `AbilityHud` snapshot); casts go through `GameEngine.activateAbility(uid)` which switches on `ability.id` (`castCycloneSlash`/`castQuickdraw`/`castManaRay`). Each ability is gated by **both** a cooldown (`Tower.abilityCooldown`, radial countdown on the icon) **and** mana. **Mana**: `UnitDef.maxMana` (all heroes = `HERO_BASE_MANA` 50) → `Tower.mana`/`maxMana` (starts full); casting spends `ability.manaCost`; the *only* refill is landing killing blows — every `EnemyDef.mana` is added to the killing hero's pool in `damageEnemy` (capped). Shown as the blue mana bar in the champion panel. Ability kinds so far: instant-AoE (Cyclone Slash — hits all in range), timed self-buff (Quickdraw — its own `abilitySpeedBuffMult`/`Timer` slot, **stacks** with the Bard's `attackSpeedBuffMult`, flares the player foot-outline), and channelled beam (Mana Ray — `Tower.beam*` fields: locked angle/range at cast, suppresses normal attacks in `updateTowers`, ticks a line-AoE every `tickInterval`, drawn slim from the hands by `drawBeams`). Ability icons are raster PNGs in `public/` (`cyclone_slash.png`/`quickdraw.png`/`mana_ray.png`) with an emoji fallback. In-stage stat panel recolours buffed stats by **category** (`.buff-spd/dmg/range/crit/dps`), not by source.
